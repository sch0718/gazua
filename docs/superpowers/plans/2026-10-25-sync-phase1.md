# 개인 동기화·읽기 공유 1단계 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 본인 Google 계정으로 로그인한 여러 기기에서 프로필(그룹·전략·선정 기준·바구니·분석 설정)을 동기화하고, 그룹·전략·선정 기준을 만료·철회되는 읽기 전용 링크로 공유해요.

**Architecture:**
- 새 Worker `sync-worker/`를 둬요. 기존 `proxy/`와 코드·배포·설정을 나누고, 증권사 호출은 넣지 않아요.
  - D1 테이블: `users`, `sessions`, `profile_index`, `profiles`, `revisions`, `shares`. `migrations/`의 SQL로 만들어요.
  - 인증: Firebase ID 토큰(`Authorization: Bearer`)을 매 요청 검증하고, 기기별 D1 세션(`X-Gazua-Session`)을 함께 확인해요.
  - 하루 한 번 Cron으로 삭제 30일이 지난 프로필·만료 공유·만료 세션을 정리해요.
- 클라이언트 `src/lib/sync/`는 Svelte에 기대지 않는 순수 TS예요.
  - `dto.ts`가 허용 필드만 담은 프로필 문서를 만들고 검증해요. Worker도 같은 검증기를 가져다 써요.
  - IndexedDB `gazua-sync`에 outbox·프로필별 동기화 상태·충돌 사본을 둬요.
  - `engine.ts`가 push(조건부 갱신)·pull(원격 적용)·충돌·tombstone을 맡아요.
  - `auth.ts`는 Firebase 웹 SDK를 **필요할 때만** 동적 import해요.
- 공유 `src/lib/share/`는 전용 스냅샷 serializer예요. 서버는 256비트 capability의 SHA-256 해시만 저장해요.
- 화면은 설정의 새 `동기화` 구역(로그인·상태·충돌·기기·삭제한 프로필·내 공유)과, 그룹·전략·선정 기준의 `공유` 버튼, 읽기 화면 `#/s/<capability>`예요.

**Tech Stack:** Svelte 5 runes, TypeScript, Vitest(+fake-indexeddb, jsdom), Cloudflare Workers + D1, `jose`(Worker의 JWT 검증), `firebase`(웹 SDK, Auth만).

**근거 문서:** docs/proposals/2026-10-25-server-and-db.md (4·6·7·8절)

## 사용자 결정 (2026-10-25)

| 항목 | 결정 |
|---|---|
| 허용 목록 | **이메일**. 검증된 토큰의 `email`이 `ALLOWED_EMAILS`(Worker secret, 콤마 구분, 소문자 비교)에 있고 `email_verified === true`일 때만 허용해요. 값은 저장소에 두지 않아요 |
| 자체 세션 | **기기별 세션, 마지막 사용 후 30일 슬라이딩 만료, 기기별·전체 철회** |

세션 정책을 이렇게 구현해요.
- 로그인 직후 `POST /v1/session`으로 기기 세션을 만들어요. 이때 토큰의 `auth_time`이 **5분 이내**여야 해요. 그래서 철회된 기기는 Firebase 갱신 토큰이 남아 있어도 Google 로그인을 다시 거쳐야 새 세션을 받아요.
- 세션 ID는 256비트 무작위 값이에요. D1에는 SHA-256 해시만 두고, 기기에는 원문을 localStorage가 아닌 IndexedDB `gazua-sync`에 둬요.
- 매 요청에서 ID 토큰과 세션을 둘 다 검사해요. 세션이 같은 사용자 것이고 철회되지 않았으며 `last_used_at + 30일 > now`여야 해요.
- `last_used_at`은 1시간에 한 번만 갱신해요. D1 쓰기 할당량을 아끼려는 거예요.
- 설정 화면에서 기기 목록을 보고 기기 하나, 또는 이 기기를 뺀 모든 기기를 철회할 수 있어요. 철회된 기기는 다음 요청에서 `401 session-revoked`를 받고 로그아웃 상태로 돌아가요. 로컬 데이터는 그대로예요.
- 로그아웃하면 이 기기의 세션도 서버에서 철회해요.

## 내가 정한 기본값 (계획 확인 때 바꿀 수 있어요)

1. **동기화 켜기:** 로그인한 뒤 `동기화 켜기`를 눌러야 시작해요. 처음 켤 때 "이 기기의 프로필 N개를 올리고, 서버의 프로필 M개를 이 기기에 추가해요"를 확인받아요. 프로필 ID가 서로 다르므로 덮어쓰기는 일어나지 않아요.
2. **공유 대상:** 그룹, 전략, 선정 기준이에요. 바구니는 선정 기준 스냅샷 안에 종목 목록으로 풀어 넣어요. **계산 결과(시뮬레이션·검증 결과) 공유는 1단계에서 빼요.** 결과 요약 형식을 따로 설계해야 해서 후속으로 남겨요.
3. **삭제된 프로필의 공유:** 프로필을 지우면 그 프로필에서 만든 공유도 바로 읽을 수 없게 해요. 복구하면 만료 전인 공유는 다시 열려요. 30일 뒤 정리할 때 함께 지워요.
4. **원격 프로필 삭제 적용:** 다른 기기에서 지운 프로필은 이 기기에서도 지워요. 이 기기에 미전송 변경이 있으면 지우지 않고 충돌로 보여 줘요(`복구하고 이 기기 것 올리기` / `이 기기에서도 지우기`).
5. **동기화 빈도:** 변경 후 3초 디바운스로 올려요. 받기는 앱 시작·탭 포커스(5분에 한 번까지)·`지금 동기화` 버튼으로만 해요. 폴링은 하지 않아요. 같은 Cloudflare 계정을 프록시·랜드마크와 함께 쓰기 때문이에요.

## Global Constraints

**보안**
- 동기화·공유 DTO에는 허용 필드만 넣어요. 서버는 같은 검증기로 다시 검사하고, 알 수 없는 필드나 금지 키가 있으면 `422`로 거절해요. 금지 키는 `appKey, appSecret, clientId, clientSecret, proxyToken, accessToken, refreshToken, secrets, token, proxyUrl, provider, keyLock, onboarded, lastGroupId, accountId, accountSeq, orders` 등이고, 어느 깊이에 있어도 막아요.
- `settings`를 통째로 복사하거나 localStorage를 순회해서 올리지 않아요. `gazua-account`·봉 캐시·시장 데이터·도움말 기록·최근 종목은 동기화하지 않아요.
- 소유자는 검증된 `sub`로만 정해요. 클라이언트가 보낸 `ownerId`는 받지 않아요. 모든 행은 `(user_id, …)`로 조회해요.
- CORS는 `ALLOWED_ORIGINS`에 정확히 일치하는 출처만 허용해요. preflight는 필요한 메서드와 `Authorization, Content-Type, X-Gazua-Session, X-Share-Token`만 허용해요. CORS는 인증을 대신하지 않아요.
- 로그에는 메서드·경로 패턴·상태·시간만 남겨요. 토큰·세션·capability·본문·이메일은 남기지 않아요.
- `proxy/`는 건드리지 않아요. 특히 `proxy/src/allowlist.ts`를 넓히지 않고, 주문 차단 테스트도 그대로 통과해야 해요.
- 결제 등록이 필요한 서비스(R2, Cloudflare Access, Firebase Blaze, Firestore)는 쓰지 않아요.
- Firebase 설정값·D1 ID·허용 이메일은 저장소에 커밋하지 않아요. `.env.local`, GitHub Actions variables, `wrangler secret`으로 넣어요. 테스트 fixture에는 지어낸 값만 써요.

**한도 (제안서 7절)**
- 프로필 문서 256 KiB, 공유 스냅샷 100 KiB, 활성 공유 50개, 프로필당 과거 리비전 10개, 공유 만료 기본 7일·최대 30일, 삭제 후 복구 30일이에요.
- 요청 본문은 300 KiB를 넘으면 읽기 전에 `413`으로 거절해요.

## D1 스키마 (`sync-worker/migrations/0001_init.sql`)

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,               -- 서버가 만든 UUID
  firebase_sub TEXT NOT NULL UNIQUE,
  email TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  last_seen_at INTEGER NOT NULL
);
CREATE TABLE sessions (
  id_hash TEXT PRIMARY KEY,          -- SHA-256(세션 원문) hex
  user_id TEXT NOT NULL REFERENCES users(id),
  label TEXT NOT NULL,               -- 기기 이름(사용자 입력, 40자)
  created_at INTEGER NOT NULL,
  last_used_at INTEGER NOT NULL,
  revoked_at INTEGER
);
CREATE TABLE profile_index (
  user_id TEXT NOT NULL REFERENCES users(id),
  profile_id TEXT NOT NULL,
  revision INTEGER NOT NULL,         -- 1부터. 0은 '없음'
  last_op_id TEXT NOT NULL,
  updated_at INTEGER NOT NULL,       -- 서버 시각
  deleted_at INTEGER,                -- tombstone
  purge_at INTEGER,                  -- deleted_at + 30일
  PRIMARY KEY (user_id, profile_id)
);
CREATE TABLE profiles (              -- 현재 본문
  user_id TEXT NOT NULL,
  profile_id TEXT NOT NULL,
  body TEXT NOT NULL,
  size INTEGER NOT NULL,
  PRIMARY KEY (user_id, profile_id)
);
CREATE TABLE revisions (             -- 현재 + 과거 10개
  user_id TEXT NOT NULL,
  profile_id TEXT NOT NULL,
  revision INTEGER NOT NULL,
  op_id TEXT NOT NULL,
  body TEXT,                         -- 삭제 리비전은 NULL
  created_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, profile_id, revision),
  UNIQUE (user_id, op_id)
);
CREATE TABLE shares (
  id TEXT PRIMARY KEY,               -- 목록·철회용 공개 ID(무작위 UUID). capability와 다름
  user_id TEXT NOT NULL REFERENCES users(id),
  token_hash TEXT NOT NULL UNIQUE,   -- SHA-256(capability) hex
  source_profile_id TEXT NOT NULL,
  kind TEXT NOT NULL,                -- 'group' | 'strategy' | 'criteria'
  title TEXT NOT NULL,
  snapshot TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL,
  revoked_at INTEGER
);
-- + 조회용 인덱스(sessions.user_id, shares.user_id, profile_index.purge_at, shares.expires_at)
```

조건부 갱신은 D1 `batch()`(한 트랜잭션)로 해요.
1. `UPDATE profile_index SET revision = ?new, last_op_id = ?op … WHERE user_id = ? AND profile_id = ? AND revision = ?expected AND deleted_at IS NULL`을 실행해요.
2. 뒤따르는 `profiles`·`revisions` 쓰기는 모두 `WHERE EXISTS (SELECT 1 FROM profile_index WHERE … AND last_op_id = ?op)` 조건으로만 적용해요.
3. 그래서 1번이 실패하면 아무것도 바뀌지 않아요. 과거 리비전 정리도 같은 batch에서 해요.
4. batch 뒤에 `last_op_id`를 읽어 성공·충돌을 판정해요.

새 프로필은 `expectedRevision: 0`일 때만 `INSERT … ON CONFLICT DO NOTHING`으로 만들어요. `expectedRevision > 0`인데 행이 없으면(30일 정리 뒤) `410 gone`이에요. 오래 오프라인이던 기기가 지운 프로필을 되살리지 못해요.

## API (`/v1`, JSON)

| 메서드·경로 | 인증 | 동작 |
|---|---|---|
| `POST /v1/session` | ID 토큰(`auth_time` 5분 이내) | 사용자 upsert, 세션 생성. `{ sessionId, expiresAt }` |
| `GET /v1/sessions` | 토큰+세션 | 내 기기 목록(`id`=해시 앞 12자, label, 시각, `current`) |
| `DELETE /v1/sessions/:id`, `DELETE /v1/sessions?others=1` | 토큰+세션 | 철회 |
| `GET /v1/profiles` | 토큰+세션 | 색인: `{ profileId, revision, updatedAt, deletedAt, purgeAt }[]` |
| `GET /v1/profiles/:id` | 토큰+세션 | `{ revision, doc }` (삭제됨이면 `410`) |
| `PUT /v1/profiles/:id` | 토큰+세션 | `{ opId, expectedRevision, doc }` → `200 { revision }` / `409 { revision, doc }` / `410 { deletedAt, purgeAt }` / `422` |
| `DELETE /v1/profiles/:id` | 토큰+세션 | `{ opId, expectedRevision }` → tombstone. 공유 읽기도 막혀요 |
| `POST /v1/profiles/:id/restore` | 토큰+세션 | `purge_at` 전이면 마지막 본문으로 되살리고 새 리비전 |
| `GET /v1/profiles/:id/revisions[/:rev]` | 토큰+세션 | 과거 리비전 목록·본문(복원용) |
| `POST /v1/shares` | 토큰+세션 | `{ sourceProfileId, kind, snapshot, ttlDays }` → `{ id, capability, expiresAt }`. capability 원문은 이때 한 번만 돌려줘요 |
| `GET /v1/shares` | 토큰+세션 | 내 공유 목록(capability 없음) |
| `DELETE /v1/shares/:id` | 토큰+세션 | 철회 |
| `GET /v1/public/share` | `X-Share-Token` | 스냅샷. 만료·철회·원본 삭제면 `410`. 항상 `Cache-Control: no-store` |

같은 `opId`로 다시 보내면 `revisions`의 `UNIQUE(user_id, op_id)`로 찾아 처음 결과를 그대로 돌려줘요. 그래서 재시도해도 리비전이 하나만 생겨요.

## 프로필 문서 DTO (`ProfileDocV1`)

```ts
{
  v: 1,
  name: string,                          // 30자
  settings: { period, metric, benchmark, perfBenchmark, colorConvention, boardOrder },
  watchlists: { groups: { id, name, items: { symbol, colorSlot, hidden, addedAt }[] }[] },
  strategies: Strategy[],
  criteria: SelectionCriteria[],
  baskets: Basket[],
}
```
- 받은 문서를 기존 sanitizer(`validWatchlists`·`sanitizeStrategies`·`sanitizeCriteria`·`sanitizeBaskets`)로 정리해요. 결과가 입력과 정확히 같아야 통과해요. 알 수 없는 필드가 있거나 고칠 것이 있으면 거절해요. 금지 키 검사는 그보다 먼저 따로 해요.
- 원격 적용은 기존 JSON 가져오기와 다른 **같은 ID 보존** 경로예요. 로컬 전용 설정(`provider, proxyUrl, venueMode, theme, keyLock, onboarded, lastGroupId`)과 키·토큰·최근 종목은 그대로 둬요.

## 공유 스냅샷 DTO (`src/lib/share/snapshot.ts`)

- `group`: `{ kind, v: 1, title, symbols: string[] }`. 숨김 종목은 빼요. 색·추가 시각·그룹 ID는 넣지 않아요.
- `strategy`: `{ kind, v: 1, title, rules }`. `rules`는 전략에서 `id, updatedAt`을 빼고, `universe: group`은 그 시점 종목 목록 `{ kind: 'symbols' }`로 풀어요. 가상 초기 자금은 미리 보기에서 보여 주고, 사용자가 `금액 빼기`를 고를 수 있어요.
- `criteria`: `{ kind, v: 1, title, rules, baskets: { name, symbols }[] }`. `pool.baskets`의 ID는 스냅샷 안 순번으로 바꾸고, `rebound.pattern.from: 'strategy'`는 `custom` entry로 풀어요.
- 프로필 이름, 다른 객체 ID, 프록시 URL, 키, 계좌, 최근 종목은 들어가지 않아요. 서버도 같은 검증기로 확인해요(알 수 없는 필드·금지 키·UUID 모양 문자열 거절).
- capability는 `crypto.getRandomValues(32바이트)`를 base64url로 바꾼 43자예요. 링크는 `https://<앱>/#/s/<capability>`이고, fragment라서 서버 로그·Referer에 남지 않아요. 읽기 화면은 이 값을 `X-Share-Token` 헤더로 보내요.
