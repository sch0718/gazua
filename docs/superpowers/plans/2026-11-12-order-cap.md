# 실계좌 주문 1회 최대 금액 — 구현계획

설계: `docs/superpowers/specs/2026-11-12-order-cap-design.md`(이하 「설계」). 설계와 다르면 설계를 따른다.

**안전 규칙:** 실제 토스 API를 주문 경로로 호출하지 않는다. 시험은 모두 가짜 fetch·임시 디렉터리로 한다. 실제 키·토큰·`.env`를 읽거나 쓰지 않는다. 맥에서 도는 프록시를 설치·재시작하지 않는다(`proxy/macos/install.sh` 실행 금지).

건드리지 않는 파일(다른 세션 작업): `src/**/tokens.css` 등 스타일, 루트 `package.json`, Playwright 스캔 스크립트, `docs/proposals/2026-11-02-external-tools.md`, `docs/roadmap.md`(마지막에 통합 세션이 고침 — 이 계획에서는 손대지 않음).

## 1. 프록시 주문 처리기 — `proxy/node/order.ts` (새 파일)

- `export interface OrderConfig`(enabled, maxAmount, dailyMaxAmount?, maxPerMinute, maxPerDay, stopFile, auditLog, disabledReason?)
- `export function readOrderConfig(env: Record<string,string|undefined>, home = homedir()): OrderConfig` — 설계 §3.6. 정수 파서: `/^[1-9]\d*$/` + `Number.isSafeInteger`. 선택 값이 있는데 틀리면 `enabled=false`, `disabledReason`에 이유. `~` → 홈. 기본값: 분당 3, 하루 20, `~/gazua-order.stop`, `~/Library/Logs/gazua-orders.jsonl`.
- `export async function createOrderHandler(cfg, deps: { fetchImpl, now: () => number, upstreamTimeoutMs: number, randomId?: () => string }): Promise<OrderHandler>` — 시작 순서(설계 §3.3 끝): 로그 열기/만들기(600, 기존 파일이면 chmod 600) → 복원(오늘 KST 건수·금액, 최근 60초 시각) → 준비. 깨진 줄·실패면 `disabledReason` 설정(주문은 `order-disabled`).
- `OrderHandler = (req: Request) => Promise<Response>`:
  - `GET /order/status` → 설계 §3.1 모양.
  - `POST /order/toss` → 설계 §3.3 1~9단계. `busy` 플래그로 처리 중이면 `409 order-busy`(줄 세우지 않음). 금액 계산은 `quantity * price`를 `Number.isSafeInteger`로 확인.
  - 상류 본문은 설계 §3.2대로 새로 만든다. 헤더는 `authorization`, `x-tossinvest-account`, `content-type: application/json`만. URL은 `UPSTREAM.toss + '/api/v1/orders'`(`proxy/src/allowlist.ts`에서 import). `redirect: 'manual'`, `AbortSignal.timeout(upstreamTimeoutMs)`.
  - 응답·오류 모양은 설계 §3.4. 3xx·토스 오류 → `order-upstream`, fetch 예외 → 502/504 + `data.clientOrderId`.
  - 다른 경로 `404 order-not-found`, 메서드 틀림 `405 method-not-allowed`.
  - 감사 로그 줄 모양은 설계 §3.5. KST 시각은 `src/lib/time/kst`의 함수를 쓰거나 `now + 9h`로 만든다(Node 번들에 브라우저 코드가 들어오지 않게 순수 함수만).
- 응답 본문은 모두 `{"error":{"code",...}}` 또는 성공 JSON. CORS 헤더는 handler가 붙인다.

## 2. 프록시 연결 — `proxy/src/handler.ts`, `proxy/node/server.ts`

- `HandleOptions`에 `order?: OrderHandler`(`MarketHandler`와 같은 타입) 추가.
- `handle`: 토큰 검사 뒤, `/market/` 분기 바로 다음에 `url.pathname === '/order' || startsWith('/order/')` 분기. `!env.PROXY_TOKEN || !opts.order` → `404 order-unavailable`. 아니면 `opts.order(req)` 결과에 `access-control-allow-origin`·`vary` 붙여 반환(market과 같은 방식). 허용 목록은 바꾸지 않는다.
- `server.ts`: `env.PROXY_TOKEN`이 있을 때만 `createOrderHandler(readOrderConfig(process.env), { fetchImpl, now: Date.now, upstreamTimeoutMs })`를 만들어 주입. `createProxyServer`는 동기이므로 서버 생성 때 초기화 프라미스를 시작만 하고, 주입하는 처리기는 준비 전이면 `GET /order/status`는 `enabled:false`, `POST /order/toss`는 즉시 `403 order-disabled`(상류 호출 0)를 돌려준다(기다리지 않음). 이를 위해 `createOrderHandler`는 `{ handler, ready: Promise<void> }`를 돌려주거나, 동기 생성 + 내부 `ready` 플래그 방식으로 만든다. 시험: 복원을 지연시킨 상태의 POST가 `order-disabled`·상류 0. `ServerOptions`에 테스트용 `orderEnv?`, `now?` 추가. 시작 시 주문 상태를 한 줄 로그(`order: on max=… / off (이유)`), 비밀값 없음.
- Worker(`proxy/src/worker.ts`)는 바꾸지 않는다(처리기 없음 → 404).

## 3. 토스 공급자 — `src/lib/providers/toss.ts`, `types.ts`

- `AccountSource`에 선택 메서드 `orderHeaders?(): Promise<{ authorization: string; 'x-tossinvest-account': string }>` 추가. 구현: 기존 토큰 관리자(`tokens.get()`)로 토큰, `/api/v1/accounts`에서 `accountType === 'BROKERAGE'`만(없으면 `ApiError('upstream', …)`로 실패). 기존 `brokerageSeq()`는 그대로.
- 시험: `src/lib/providers/toss.account.test.ts`에 설계 §6 마지막 세 항목.

## 4. CLI — `cli/src/commands/order.ts` (새 파일)과 연결

- `args.ts`: `yes: boolean` 옵션(`--yes`) 추가.
- `errors.ts` `MESSAGES`: `order-not-configured`, `order-disabled`, `order-stopped`, `order-over-limit`, `order-daily-limit`, `order-rate-limited`, `order-busy`, `order-invalid`, `order-unavailable`, `order-upstream`, `order-unknown`, `order-audit-failed`(「맥 감사 로그를 쓸 수 없어 보내지 않았어요」), `proxy-rejected`(「프록시가 거절했어요. GAZUA_PROXY_TOKEN·GAZUA_PROXY_ORIGIN을 확인해 주세요」) 추가(설계 §4 문구).
- 프록시 오류 변환은 명시적 표로 한다: 위 `order-*` 코드는 같은 이름, `proxy-token-invalid`·`origin-not-allowed` → `proxy-rejected`, 그 밖에 모르는 코드나 본문 → 주문 POST면 `order-unknown`(결과 불명), 상태 GET이면 `upstream`. `proxy-redirect`는 기존처럼 `upstream`으로 바뀌어도 되지만 주문 POST의 3xx는 `order-unknown`.
- `execute.ts`: `COMMANDS.order` 등록, `SECRET_ENV`에 `GAZUA_PROXY_TOKEN` 추가.
- `order.ts`:
  1. 인자 `buy|sell <6자리> <수량> <지정가>`(양의 정수 `/^[1-9]\d*$/`, 안전한 정수) → 아니면 `invalid-args`.
  2. `GAZUA_PROXY_URL`(→ `normalizeServer`), `GAZUA_PROXY_TOKEN`, `GAZUA_PROXY_ORIGIN` 없으면 `order-not-configured`. 토큰은 `ctx.redact.add`.
  3. `GET <url>/order/status`(헤더 `origin`, `x-proxy-token`, `redirect:'manual'`). 실패 응답은 `error.code`를 CliError로.
  4. `--yes` 없으면 설계 §4 요약 반환(`sent:false`). 주문 POST 없음.
  5. `--yes`면 `buildProvider(ctx,'toss',creds).provider.account?.orderHeaders` 존재를 확인(없으면 `provider-unsupported`)한 뒤 `orderHeaders()`(토큰·accountSeq는 `ctx.redact.add`) → `POST <url>/order/toss` JSON 본문 `{symbol,side,quantity,price}`. 자동 재시도 없음.
  6. 응답: 200 → `{sent:true, orderId, clientOrderId, amount}`. 프록시 오류 코드는 같은 이름의 CliError(`data` 포함, `order-over-limit`은 금액을 문구에 넣음). 502·504·3xx·fetch 예외·JSON 해석 실패 → `order-unknown`(+`clientOrderId`가 있으면 data).
- `main.ts` 머리 주석 고침.
- MCP: `cli/src/mcp/tools.ts`는 바꾸지 않는다. `tools.test.ts` 24행 제외 목록에 `'order'`를 더하고, `order`가 `TOOLS`에 없다는 시험을 하나 둔다.

## 5. 시험

- `proxy/node/order.test.ts`: 설계 §6 프록시 항목 전부. 임시 디렉터리에 감사 로그·중지 파일, 가짜 fetch(`vi.fn`), `now` 주입.
- `proxy/src/handler.test.ts`: `/order/toss` 토큰 없음·틀림 401, `PROXY_TOKEN` 없음 404, 처리기 없음(Worker) 404, `/toss/api/v1/orders` POST 403.
- `proxy/node/server.test.ts`: 서버가 주문 처리기를 주입했을 때 `/order/status`가 200이고, `PROXY_TOKEN` 없으면 404(가짜 fetch).
- `cli/src/commands/order.test.ts`: 설계 §6 CLI 항목. `makeIo`·`fakeFetch`(`cli/src/testing.ts`). 토스 토큰·계좌 응답도 가짜. `FakeCall`에는 `redirect`가 없으므로 `cli/src/testing.ts`의 `FakeCall`에 `redirect?: RequestRedirect`를 기록하도록 더한다(기존 시험은 그대로 통과해야 함).
- `cli/src/readme.test.ts`가 새 명령·오류 코드·환경변수를 README에 요구하므로 README를 같이 고친다.
