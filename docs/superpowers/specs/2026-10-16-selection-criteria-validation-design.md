# 선정 기준 검증 설계 (1단계)

작성 2026-10-16. 기반 스펙: [비교 화면](2026-10-11-stock-compare-design.md), [매매 규칙 시뮬레이션](2026-10-12-backtest-simulation-design.md).

## 1. 목표와 범위

### 1.1 목적

사용자가 **자기가 종목을 고르는 기준이 괜찮은지 확인**하는 기능이다. 매매 규칙 시뮬레이션이 "언제 사고파는가"를 검증한다면, 이 기능은 "무엇을 고르는가"를 검증한다.

과거의 여러 시점으로 돌아가, **그 시점까지의 데이터만으로** 기준을 적용해 종목을 고른다. 그렇게 고른 종목들이 이후 어떤 성과를 냈는지 시장 지수와 비교 ETF에 견준다. 기준이 괜찮다고 판단되면, 오늘 기준으로 고른 종목을 관심 그룹에 넣을 수 있다(부가 기능).

**성공 기준.** 기준 하나를 정해 실행하면 다음 두 가지를 숫자와 곡선으로 바로 읽을 수 있다.
- 이 기준으로 고른 종목이 시장 지수와 비교 ETF보다 나았나
- 내 매매 규칙까지 더하면 어땠나

### 1.2 대화에서 확정한 것 (2026-10-16)

| 항목 | 결정 |
|---|---|
| 기능의 성격 | 종목 추천 도구가 아니라 **선정 기준 검증** 도구다. 오늘 기준 선별과 관심 그룹 넣기는 부가 기능이다. |
| 찾는 종목 | 후보를 추린 뒤(규모·업종 등), 그중 내 매수 패턴(저점 확인 후 반등)이 나타난 종목 |
| 검증 원칙 | 과거 시점 선별(point-in-time). 그 시점 **전날까지**의 데이터만 쓴다. |
| 검증 방식 | ① 선정만(동일 비중 보유)과 ② 선정 + 내 매매 규칙(기존 엔진)을 **나란히** 보인다. |
| 데이터 | 사용자가 **원할 때 자기 컴퓨터에서 수집 스크립트를 실행**한다. 결과 파일을 앱에서 가져와 브라우저에 저장한다. 저장소에는 커밋하지 않는다. |
| 대상 종목 | 전 종목. KOSPI·KOSDAQ, 주식과 ETF·ETN·리츠를 포함한다. ETF는 고르는 대상도 되고 비교 대상도 된다. |
| 시장별 보기 | 같은 기준을 KOSPI·KOSDAQ·ETF 범위로 따로 돌린 결과를 함께 보인다. |
| 수집 기간 | 기본 최근 5년. 옵션으로 바꿀 수 있다. |
| 화면 위치 | 시뮬레이션 화면 안의 `선정 기준` 탭. 새 최상위 메뉴는 없다. |

사용자가 평소 보는 기준은 외국인·기관·개인 매매동향, 산업군별 대장주, 저점 확인 후 반등 추세, 환율·유가 영향도, 회사 규모·거래량, 가격 흐름, 재무·가치, 업종·테마다. 그중 일봉과 종목 마스터로 계산할 수 있는 것을 1단계로 하고, 나머지는 데이터 확인 후 단계별로 붙인다(9장).

### 1.3 범위 밖 (이번 단계)

- 재무·가치, 투자자 매매동향, 환율·유가 영향도, 직접 만드는 테마 묶음. 2~4단계로 넘긴다(9장).
- 상장폐지 종목. 마스터 파일이 현재 상장 종목만 준다.
- 과거 시점의 업종 분류와 상장주식수 이력. 수집일 값을 쓴다.
- 비교 화면과 매매 규칙 시뮬레이션이 수집 파일을 쓰는 것. 지금처럼 API로 받는다.
- 배당·세후 수익률(시뮬레이션과 같음), 분봉, 주문.

## 2. 구조

```
[내 컴퓨터] pnpm collect ──(KIS 키: 환경변수)──▶ KIS Open API (직접 호출, 프록시 없음)
     │ market-data-YYYYMMDD.json.gz   (저장소 밖, 커밋하지 않음)
     ▼
[앱] 설정 › 데이터 › 시장 데이터 가져오기 ──▶ IndexedDB (기기마다)
     ▼
[선정 기준 탭] 기준 편집 ─ 검증 실행 ─▶ Web Worker
     │                          ├ 지표 미리 계산 (종목마다 날짜순 한 번)
     │                          ├ 재선정일마다 selectAt()
     │                          ├ ① 동일 비중 보유  holdSelection()
     │                          ├ ② 기존 엔진 simulate() + 매수 가능 기간
     │                          └ 비교: 지수·ETF 보유 곡선
     ▼
[결과] 요약 · 곡선 · 시장별 표 · 선정 이력 · 오늘 기준 선별 → 관심 그룹
```

- 계산은 모두 순수 함수다. 네트워크와 화면을 모른다. Worker는 이 함수들을 부르고 진행률만 보낸다.
- 프록시와 서버는 바꾸지 않는다. 수집 스크립트는 사용자 컴퓨터에서 KIS에 직접 붙는다.

## 3. 데이터 수집 스크립트

### 3.1 실행

```bash
KIS_APP_KEY=... KIS_APP_SECRET=... pnpm collect -- --years 5 --out ~/gazua-data/
KIS_APP_KEY=... KIS_APP_SECRET=... pnpm collect -- --update ~/gazua-data/market-data-20261016.json.gz
```

- 파일은 `scripts/collect-market-data.mjs`다. Node 22에서 돌고, 런타임 의존성은 새로 넣지 않는다(내장 `fetch`, `zlib`). 마스터 zip을 푸는 데는 기존 devDependency인 `fflate`를 쓰므로 `pnpm install`이 된 저장소에서 돌린다.
- **받는 끝 날짜.** 평일 KST 18시 전이면 아직 끝나지 않은 오늘 봉을 받지 않고 전날까지 받는다. 그 밖에는 오늘까지 받는다.
- 키 형식(공백·줄바꿈·한글이 없는 ASCII)을 시작할 때 검사하고, 틀리면 값을 되풀이하지 않고 거부한다. 로그에 나가는 모든 오류 문구는 키·토큰을 `***`로 가린다. 요청마다 20초 제한을 두고 시간 초과·네트워크 오류·본문이 끊기거나 형식이 틀린 응답은 최대 4번 다시 시도한다(빈 페이지로 오해해 기록을 자르지 않는다). 토큰 발급만은 다시 시도하지 않고 바로 멈춘다. KIS가 1분에 1회로 제한해 서둘러 재발급하면 오히려 막히기 때문이다.
- 키는 **환경변수로만** 받는다. 파일·로그·출력·오류 메시지에 키나 토큰을 쓰지 않는다. 토큰은 실행 동안 메모리에만 둔다. KIS 1분 1회 발급 제한을 지키도록 실행당 한 번 발급한다.
- 요청 속도는 초당 18건을 넘지 않는다(KIS 한도 20건에 여유). 429나 `EGW00201`을 받으면 기존 큐와 같은 규칙으로 쉰다.
- 실전/모의 서버를 고르는 `--paper` 옵션이 있다. 기본은 실전이다(`openapi.koreainvestment.com:9443`, 모의 `openapivts.koreainvestment.com:29443`).
- 기본 출력 폴더는 `~/gazua-data/`다. 저장소 안이면 `.gitignore`에 있는 `data/`만 허용하고, 그 밖의 저장소 경로는 거부한다.

### 3.2 받는 것

| 데이터 | 출처 | 비고 |
|---|---|---|
| 종목 목록, 시장, 종류 | KIS 마스터 `kospi_code.mst`, `kosdaq_code.mst` | `scripts/parse-master.mjs`를 확장한다 |
| 업종 대·중·소 코드와 이름 | 마스터 tail 오프셋 3·7·11(각 4바이트), 이름은 `idxcode.mst` | **수집일 기준**. 코드 변환은 아래 규칙 |
| 상장주식수(천 주) | 마스터 tail(KOSPI 113:15, KOSDAQ 108:15) | **수집일 기준**. 단위는 실연결 점검으로 확정한다(8.3) |
| 관리종목, 거래정지 | 마스터 tail(KOSPI 62·60, KOSDAQ 57·55) | **수집일 기준** |
| 종목 일봉(수정주가) | `inquire-daily-itemchartprice`(FHKST03010100), 시장 `J` | 시가·고가·저가·종가·거래량·거래대금 |
| 지수 일봉 | 기존 지수 일봉 TR(KOSPI `0001`, KOSDAQ `1001`) | 시가(`bstp_nmix_oprc`)·종가(`bstp_nmix_prpr`). 비교 기준과 거래일 축 |

- 마스터의 매출·영업이익·ROE·시가총액 필드는 **받지 않는다.** 현재 스냅샷뿐이라 과거 시점 검증에 섞이면 미래 정보가 된다. 단위와 기간이 불분명하고, 당기순이익 필드는 폭이 의심스럽다는 이유도 있다.
- 일봉 TR은 한 번에 100행 안팎을 준다. 기간을 나눠 거슬러 받는다.
- **업종 코드 변환(2026-10-16 실제 파일로 확인).** 마스터 tail의 4자리 코드 앞에 시장 숫자(KOSPI `0`, KOSDAQ `1`)를 붙이면 `idxcode.mst`의 5자리 코드가 된다.
  - 예: 삼성전자 tail `0027`·`0013` → `00027` 제조·`00013` 전기·전자. 에코프로비엠(247540) tail `1009`·`1028` → `11009` 제조·`11028` 전기·전자(KOSDAQ tail은 이미 `1`로 시작한다). 마스터 종목의 업종 슬롯 4,202개(0000 제외)가 모두 이 규칙으로 `idxcode.mst`에서 이름이 찾아진다.
  - `0000`과 `idxcode.mst`에 없는 코드는 `''`(없음)로 둔다.
  - 파일의 `sec`와 `sectors[].code`는 이 5자리 코드다. `sectors`에는 종목이 실제로 쓰는 코드만 넣고, `level`은 그 코드가 나타난 슬롯(1 대분류, 2 중분류, 3 소분류) 중 가장 낮은 값이다.

### 3.3 이어 받기와 수정주가

- `--update <파일>`을 주면 종목마다 마지막 날짜 다음 날부터 받아 합친다.
- 합칠 때 **겹치는 마지막 5거래일**을 다시 받아 기존 값과 비교한다. 다르면 액면분할 등으로 수정주가가 바뀐 것이므로, 그 종목만 전체 기간을 다시 받는다.
- 새로 상장한 종목은 전체 기간을 받는다. 마스터에서 빠진 종목(상장폐지)은 기존 파일에서도 뺀다. 상장폐지 종목 데이터를 남겨 생존 편향을 줄이고 싶다면 남길 수도 있지만, 이번 단계에서는 빼고 그 한계를 안내한다.
- 중간에 끊기면 `<출력 파일>.partial`(예: `market-data-20261016.json.gz.partial`)에 진행분을 남기고, 다시 실행하면 이어서 받는다. 형식은 JSON Lines(첫 줄 헤더, 이후 끝난 종목·지수마다 한 줄)다. **같은 날 다시 실행할 때만** 이어지고, 헤더의 기간과 `--update` 원본 파일 경로가 지금 실행과 같아야 한다. 이어 받기 전에 온전한 줄만 남기고 파일을 다시 쓴다. 완료되면 `.tmp`에 스트리밍으로 쓴 뒤 원자적으로 이름을 바꾸고 `.partial`을 지운다.
- 거래정지로 가격이 0인 날은 파일에서 뺀다(그 날짜의 봉이 없는 것으로 본다). 페이징은 가격이 유효한지와 무관하게 받은 날짜로 진행해, 100거래일 넘는 정지가 있어도 앞의 기록을 받는다. `--update`에서 다시 받은 결과가 비면 그 종목의 기존 기록을 그대로 두고 실패로 알린다.

### 3.4 출력 형식

`market-data-YYYYMMDD.json.gz`. 압축 해제하면 JSON이다.

```ts
interface MarketDataFile {
  format: 'gazua-market-data';
  version: 1;
  collectedAt: string;              // ISO, KST
  source: 'kis';
  adjusted: true;                   // 수정주가
  range: { from: string; to: string };   // YYYY-MM-DD
  sectors: { code: string; name: string; level: 1 | 2 | 3 }[];   // code는 5자리(3.2). level은 나타난 가장 낮은 슬롯
  stocks: {
    s: string; n: string;           // 코드, 이름
    m: 'KOSPI' | 'KOSDAQ';
    t: 'STOCK' | 'ETF' | 'ETN' | 'REIT' | 'OTHER';
    sec: [string, string, string];  // 업종 대·중·소 5자리 코드(시장 숫자 + tail, 3.2). '' = 없음
    shares: number;                 // 상장주식수(주). 수집일 기준
    managed: boolean; halted: boolean;   // 수집일 기준
    d: string[];                    // 날짜(YYYYMMDD) 오름차순
    o: number[]; h: number[]; l: number[]; c: number[]; v: number[]; tv: number[];  // 거래대금(원)
  }[];
  indices: { id: 'KOSPI' | 'KOSDAQ'; d: string[]; o: number[]; c: number[] }[];  // 시가는 비교 곡선의 첫날 기준값(indexCurve)에 쓴다
}
```

- 열 지향 배열로 두어 크기를 줄인다. 5년 전 종목이면 압축 후 수십 MB로 예상한다. 첫 수집 때 실제 크기를 재서 README에 적는다.
- 스크립트 끝에 요약을 출력한다: 종목 수, 기간, 다시 받은 종목 수, 실패 종목(코드만), 소요 시간, 파일 크기.

## 4. 앱: 데이터 가져오기와 보관

- 설정 › 데이터에 `시장 데이터 가져오기`를 둔다. 파일을 고르면 `DecompressionStream('gzip')`으로 풀고 검증한 뒤 IndexedDB(`gazua-market-data` DB)에 저장한다.
- **검증 항목.** 다음 중 하나라도 어긋나면 저장하지 않고 이유를 알린다: `format`·`version`, 배열 길이 일치, 날짜 오름차순, 가격 > 0, 유한한 숫자.
  - `version`이 더 높으면: `새 형식의 파일이에요. 앱을 새로 고친 뒤 다시 가져와 주세요`
  - 손상된 경우: `파일을 읽을 수 없어요. 수집을 다시 해 주세요`
- 프로필과 무관한 **기기 단위** 데이터다. 키가 없는 시세 데이터라 잠금(키 암호화)과도 무관하다.
- 저장 공간.
  - 가져오기 전에 `navigator.storage.estimate()`로 여유를 확인한다. 부족하면 `저장 공간이 부족해요(필요 약 n MB)`라고 알린다.
  - `navigator.storage.persist()`를 요청한다. 거절되면 `브라우저가 공간이 부족할 때 지울 수 있어요`라고 안내한다.
- 표시: `수집 2026-10-16 · 4,312종목 · 2021-10-15 ~ 2026-10-15`. `지우기` 버튼이 있다.
- 수집일이 30일 넘게 지나면 선정 기준 탭 위에 `데이터가 n일 전 것이에요. 최근 기간은 검증에 빠져요`를 표시한다. 닫기는 되지만 다음 실행에 다시 뜬다.
- 내보내기·가져오기(설정 › 데이터)의 기존 JSON에는 시장 데이터를 넣지 않는다. 크기 때문이다. 시장 데이터는 수집 파일 자체가 이동 수단이다.

## 5. 선정 기준 모델

모든 숫자는 사용자가 바꿀 수 있다. 괄호 안이 기본값이다.

```ts
interface SelectionCriteria {
  id: string;
  name: string;                         // 30자 이내
  updatedAt: number;
  pool: {
    markets: ('KOSPI' | 'KOSDAQ')[];    // (둘 다), 빈 배열 불가
    types: ('STOCK' | 'ETF')[];         // (['STOCK']), 빈 배열 불가. ETN·REIT·OTHER는 이번 단계에서 고르지 않는다
    excludeManaged: boolean;            // (true) 관리종목·거래정지 제외(수집일 기준)
    sectors: string[];                  // 업종 대·중 코드, 빈 배열 = 전체
  };
  conditions: {
    marketCap:   { on: boolean; minEok: number };                 // (끔, 1000) 억 원
    tradingValue:{ on: boolean; days: number; minEok: number };   // (켬, 20, 10) 평균 거래대금 억 원
    leader:      { on: boolean; level: 1 | 2; maxRank: number };  // (끔, 1, 3) 업종 안 시가총액 순위
    returnRange: { on: boolean; days: number; minPct: number; maxPct: number }; // (끔, 60, -30, 0)
    vsMa:        { on: boolean; period: number; side: 'above' | 'below' };      // (끔, 60, 'above')
    fromHigh:    { on: boolean; minPct: number; maxPct: number }; // (끔, 20, 50) 52주(250거래일) 종가 고점 대비 하락폭
    volatility:  { on: boolean; days: number; maxPct: number };   // (끔, 20, 3) 일간 수익률 표준편차
    rebound:     { on: boolean; withinDays: number;               // (켬, 10)
                   pattern: { from: 'strategy'; strategyId: string } | { from: 'custom'; entry: Strategy['entry'] } };
  };
  rank: { by: 'marketCap' | 'tradingValue' | 'return' | 'lowVolatility'; take: number }; // ('marketCap', 10), take 1~30
  rebalance: 'monthly' | 'quarterly' | 'semiannual';      // ('monthly')
  period: { from: string; to: string };                   // 데이터 범위 안. 기본: 데이터 시작 + 1년 ~ 데이터 끝
  benchmarks: { indices: ('KOSPI' | 'KOSDAQ')[]; symbols: string[] }; // ([KOSPI], ['069500']), symbols 최대 3
  costs: { feePct: number };                               // (0.015) 매수·매도 각각
  capital: number;                                         // (10_000_000)
  trading: { strategyId: string | null };                  // ② 매매 규칙. null이면 ②를 돌리지 않는다
}
```

- 켠 조건을 **모두** 만족해야 통과한다(AND).
- 저장은 `p:<profile>:criteria`. 전략과 같은 손상 처리 규칙을 따른다: 깨진 항목은 기본값으로 되돌리고 손상 안내를 띄운다(`repaired`). 프로필 내보내기·가져오기에 포함한다.
- 반등 조건의 패턴 설정은 실행 전에 실제 `entry`로 해석한다(`resolveReboundEntry`): `from === 'strategy'`면 저장된 전략의 `entry`, `'custom'`이면 그 값. 계산 함수(precompute)는 해석된 `entry`만 받는다.
- `rebound.pattern.from === 'strategy'`이거나 `trading.strategyId`가 가리키는 전략이 지워지면, 편집 화면에서 다시 고르게 한다. 실행은 막는다.

### 5.1 조건 계산

모든 값은 **재선정일 d의 전 거래일 p까지**의 봉만으로 계산한다. 그날(d) 봉은 쓰지 않는다.

| 조건 | 계산 | 봉이 모자랄 때 |
|---|---|---|
| 시가총액 | `c[p] × shares` | 통과하지 않음 |
| 거래대금 | `p`까지 최근 `days`개 `tv`의 평균 | 통과하지 않음 |
| 대장주 | 같은 업종(레벨 1 또는 2) 안에서 시가총액 순위. 후보 범위와 다른 조건을 적용하기 **전** 전체 종목 기준 | 업종 코드가 없으면 통과하지 않음 |
| 수익률 | `c[p] / c[p - days] − 1` | 통과하지 않음 |
| 이동평균 | `c[p]`와 `p`까지 `period`일 단순이동평균 비교 | 통과하지 않음 |
| 52주 고점 대비 | `1 − c[p] / max(c[p-249..p])` | 250개 미만이면 있는 만큼(최소 120개) |
| 변동성 | `p`까지 `days`개 일간 수익률의 표본 표준편차 | 통과하지 않음 |
| 반등 신호 | 시뮬레이션 패턴 추적기(`pattern.ts`)를 그 종목에 날짜순으로 돌려, 매수 신호일이 `[p − withinDays + 1, p]` 안에 있으면 통과 | 패턴 워밍업 규칙을 따름 |

- 거래정지 등으로 `p`에 봉이 없는 종목은 그 재선정에서 통과하지 않는다.
- 수익률 기준 정렬(`rank.by = 'return'`)은 `returnRange.days`를 쓴다. 조건이 꺼져 있으면 60일이다.
- 낮은 변동성 정렬은 `volatility.days`를 쓴다. 꺼져 있으면 20일이다.
- 거래대금 정렬은 조건이 꺼져 있어도 `tradingValue.days`를 쓴다.
- 봉이 모자라 정렬 값이 없는 종목은 통과했더라도 맨 뒤로 보낸다.
- 이동평균 비교는 엄격하다: `above`는 `c[p] > 평균`, `below`는 `c[p] < 평균`.
- 정렬이 같으면 종목코드 오름차순으로 정한다.

### 5.2 재선정일

- 검증 기간 안에서, 거래일 축(지수 날짜 ∪ 종목 날짜)의 매월·분기·반기 첫 거래일이다.
- 기간 시작일이 거래일이 아니면 그 뒤 첫 거래일이 첫 재선정일이다.
- 마지막 재선정 구간은 기간 끝날 종가까지다.

## 6. 검증 계산

### 6.1 선별 `selectAt`

```ts
function selectAt(d: string, ctx: PrecomputedData, c: SelectionCriteria): Selection;
interface Selection {
  date: string;
  passed: number;                       // 조건 통과 수
  picked: { symbol: string; values: Record<string, number | boolean | null> }[];
}
```

- 후보 범위 → 조건 → 정렬 → 상위 `take` 순서다. `values`에는 각 조건의 계산값을 남긴다. 선정 이력에서 이유를 보여 주는 데 쓴다.
  - 키: 켠 조건의 `marketCap`(원), `tradingValue`(원), `leaderRank`, `return`(%), `ma`(평균값), `fromHigh`(%), `volatility`(%), `rebound`(true)와 정렬 기준 값(`lowVolatility`는 `volatility`).
- 지표는 종목마다 날짜순으로 **한 번** 미리 계산해 Worker 메모리에 둔다(이동평균, 이동 표준편차, 롤링 최대, 패턴 신호일 목록). `selectAt`은 종목마다 p를 이분 탐색으로 찾고(O(log n)), 대장주 조건이 켜져 있으면 날짜마다 업종별로 시가총액 정렬을 한 번 한다.
- 미리 계산은 쓴 기준 값(거래대금 일수, 이동평균 기간, 변동성 일수, 반등 패턴)을 함께 둔다. `selectAt`에 그와 다른 기준이 오면 `PrecomputeMismatchError`를 던진다. `poolOverride`(시장·종류)는 미리 계산과 무관하다.

### 6.2 ① 선정만: 동일 비중 보유 `holdSelection`

- 재선정일 d의 **시가**에, 그 구간 자산을 고른 종목 수로 나눠 같은 금액씩 산다. 수량은 정수 주이고, 시뮬레이션의 `maxShares` 규칙을 쓴다.
- 다음 재선정일 시가에 전부 팔고 새로 산다. 같은 종목이 다시 뽑히면 수량 차이만 거래한다. 수수료는 거래한 수량에만 붙는다.
- 매수·매도 수수료(`feePct`)와 매도세는 시뮬레이션의 세율표와 결제일(T+2) 기준을 그대로 쓴다. 돈 계산은 `roundMoney` 규칙을 따른다.
- **재선정일 d에 봉이 없어 시가 매수를 할 수 없는 종목**(전 거래일 p까지는 거래되다 d부터 거래정지 등): 그 종목에 배정한 금액은 **그 구간 동안 현금으로 둔다.** 다른 종목에 다시 나누지 않고, 구간 중간에 늦게 사지도 않는다. 선정 이력에 `매수 못 함(재선정일 거래 없음)`으로 표시한다. ②도 엔진 규칙상 그날 봉이 없으면 사지 못하므로 두 방식의 가정이 같다.
- 구간 중간에 봉이 끊긴 종목은 마지막 종가로 평가한다. 다음 재선정일에 봉이 없으면 마지막 종가로 판 것으로 계산하고 표시한다.
- 통과 종목이 0개인 구간은 현금으로 둔다.
- 배정 금액으로 1주도 못 사는 종목도 봉이 없는 종목과 같이 못 산 것으로 둔다(`notBought`).
- 재선정일에 봉이 없는 보유 종목(다시 뽑혔어도)은 마지막 종가로 팔고, 그 매도세율은 재선정일의 결제일(T+2) 기준이다(마지막 봉이 있던 해가 아니다).
- 재선정일 자산 총액은 매도 수수료·세금을 빼지 않는다. 그래서 현금이 모자라면 뽑힌 순서의 마지막 매수가 줄어들고, 0주가 되면 `notBought`다.
- "지수보다 나은 구간 수"는 구간 양 끝 날짜의 ① 순자산(수수료·세금 포함) 수익률을 지수 수익률과 비교한다. 첫 구간은 둘 다 초기 자본에서 시작한다.
- 자산 곡선은 매 거래일 종가 평가다.

### 6.3 ② 선정 + 매매 규칙

기존 엔진 `simulate()`를 쓴다. 입력에 **선택 필드 하나**를 더한다.

```ts
// src/lib/sim/types.ts  SimInput.stocks[i]
buyWindows?: { from: string; to: string }[];   // 양끝 포함. 없으면 지금처럼 항상 매수 가능
```

- 매수 신호(첫 매수와 분할 매수)는 그날이 어떤 `buyWindows` 안에 있을 때만 체결한다. 매도(손절·익절)는 창과 상관없이 계속 처리한다.
- 창 밖에서 생긴 매수 신호는 건너뛴 것으로 기록한다(사유 `선정 기간이 아니에요`). 창 판정은 **체결일** 기준이다(신호 다음 날 시가 체결이므로 창 마지막 날의 신호는 건너뛴다). 사려던 것이 현금 부족 등 다른 사유로 먼저 막히면 그 사유를 남기고, 같은 날·종목·사유는 한 번만 기록한다. 패턴 추적기는 창과 무관하게 계속 돈다.
- `stocks`는 기간 중 한 번이라도 뽑힌 종목 전부다. 창은 각 재선정 구간 `[d, 다음 재선정일 전날]`이다.
- **기존 전략 실행과의 호환.** `buyWindows`가 없으면 결과가 지금과 같아야 한다. 같은 입력에서 같은 결과가 나오는지를 테스트로 고정한다.
- 기존 전략의 "최대 8종목" 제한은 전략 편집의 제한이다. 엔진에는 제한이 없으므로 ②는 30종목 이상도 받는다. 자금 배분은 전략의 `perBuyPct`를 따른다.
- 참조 전략에서 **매수·매도 규칙(`entry`, `scaleIn`, `exit`)과 1회 매수 비율(`capital.perBuyPct`)만** 가져온다. 나머지는 선정 기준 값으로 바꿔 ①과 같은 조건으로 돌린다: `period` ← 기준 기간, `capital.initial` ← `criteria.capital`, `costs.feePct` ← `criteria.costs.feePct`, `benchmarks` ← 기준의 첫 지수(비교 곡선은 6.4에서 따로 만든다). 그래야 초기 자본·수수료 차이로 정수 주와 1회 매수금액이 달라져 ①과 ②가 어긋나는 일이 없다.

### 6.4 비교 기준

- 지수: 수집 파일의 지수 시가·종가로 봉(`{ t, o, h: max(o,c), l: min(o,c), c, v: 0 }`)을 만들어 시뮬레이션의 `indexCurve`에 넣는다. 첫날 시가가 분모라 ①(첫 재선정일 시가 매수)과 시작 기준이 같다.
- 지정 종목·ETF(최대 3개): 수집 파일의 일봉으로 기간 첫날 시가에 사서 끝까지 보유한다(`singleCurve`). 수수료를 포함한다.
- 지정 종목이 수집 파일에 없거나 기간 일부만 있으면 `받지 못함`으로 표시한다(시뮬레이션 6.1과 같은 규칙).

### 6.5 시장별 보기

같은 기준에서 `pool.markets`와 `pool.types`만 바꿔 ①을 따로 돌린다.
- KOSPI 주식
- KOSDAQ 주식
- ETF(종류를 ETF로)

후보 범위에 원래 없던 시장도 계산해서 비교로 보인다. 행마다 원래 범위인지 표시한다.

### 6.6 지표

곡선마다 다음을 계산한다.
- 총수익률, 연환산 수익률(CAGR), 최대 낙폭, 변동성(연환산)
- 지수 대비 초과수익(총수익률 차)
- ①은 추가로 "재선정 구간 중 지수보다 나은 구간 수 / 전체 구간 수"와 평균 선정 종목 수를 낸다.

### 7.3 기준 편집

섹션 순서는 다음과 같다.

3. 고를 개수·정렬
4. 재선정·기간
5. 비교 대상
6. ② 매매 규칙

- 조건마다 켜기 토글과 한 줄 설명을 단다. 문구는 아래 표와 같다.

  | 조건 | 설명 |
  |---|---|
  | 시가총액 | `회사 전체의 값어치예요. 클수록 큰 회사예요.` |
  | 거래대금 | `하루에 거래된 금액이에요. 크면 사고팔기 쉬워요.` |
  | 대장주 | `같은 업종에서 시가총액이 몇 등 안에 드는지예요.` |
  | 수익률 | `최근 며칠 동안 얼마나 오르거나 내렸는지예요.` |
  | 이동평균 | `최근 며칠 평균 가격보다 위에 있는지예요. 위면 오르는 흐름이에요.` |
  | 52주 고점 대비 | `1년 중 가장 높았던 가격에서 얼마나 내려와 있는지예요.` |
  | 변동성 | `하루 가격이 얼마나 출렁이는지예요. 작을수록 잔잔해요.` |
  | 반등 신호 | `하락이 이어지다 저점을 찍고 반등하는 내 매수 패턴이 최근에 나타났는지예요.` |

- 업종 고르기는 대분류 목록과 펼치는 중분류 목록이다. 이름은 수집 파일의 업종 이름이다.
- 반등 신호의 패턴 설정은 `전략에서 불러오기`(저장된 전략 선택)와 `직접 정하기`(전략 편집의 매수 섹션과 같은 컴포넌트) 중 고른다.
- 맨 아래 `오늘 기준 미리 보기`: 데이터 마지막 날 기준으로 `통과 n개 · 상위 10개`와 종목 이름을 보인다. 편집하면 0.3초 뒤 다시 계산한다(Worker).
- 저장과 실행 버튼은 전략 편집과 같은 위치·규칙이다.
- 입력 검증은 다음과 같다.
  - 범위 밖 숫자는 저장을 막지 않고 필드 아래에 오류를 표시한다. 실행은 막는다.
  - 켠 조건이 하나도 없으면 `조건이 없으면 후보 범위의 모든 종목에서 정렬 순으로 골라요`를 경고로 보인다. 막지는 않는다.

### 7.4 실행과 결과

- 실행하면 진행 `재선정일 계산 중 14/48`과 `취소`를 보인다. Worker를 쓰므로 화면은 계속 반응한다.
- 결과 화면은 위에서 아래로 다음 순서다.
  1. **오늘 기준 선별**
     - 상위 N개 목록과 `관심 그룹으로 만들기`가 있다.
     - 관심 그룹은 최대 8종목(`MAX_ITEMS`)이므로, 위에서부터 8개를 넣는다. 나머지가 있으면 `상위 8개만 넣었어요`를 표시한다.
     - 새 그룹 이름 기본값은 기준 이름이다. 기존 그룹에 더하기도 된다(빈자리만큼).
  2. **요약 카드**
     - ①, ②, 지수, ETF 각각의 총수익률, CAGR, 최대 낙폭, 지수 대비를 보인다.
     - ①은 `지수보다 나은 구간 m/n`도 보인다.
     - ②가 없으면 `매매 규칙을 고르면 함께 볼 수 있어요`를 표시한다.
  3. **자산 곡선**
     - 기존 차트 스타일과 색 규칙을 따르고 범례로 켜고 끈다.
     - 재선정일은 세로 눈금으로 표시한다.
  4. **시장별 표**: KOSPI 주식, KOSDAQ 주식, ETF 행에 ① 총수익률, 최대 낙폭, 평균 선정 수, 지수 대비를 보인다.
  5. **선정 이력**
     - 재선정일마다 통과 수, 뽑힌 종목, 그 구간 종목별 수익률을 보인다.
     - 행을 펼치면 조건 계산값이 나온다.
     - 통과가 0개면 `통과 0개 · 현금`으로 표시한다.
  6. **해석 도움말 (항상 표시)**
     - `지금 상장된 종목만 들어 있어 상장폐지 종목이 빠져요(생존 편향). 결과가 실제보다 좋게 나올 수 있어요`
     - `업종과 상장주식수는 수집일 기준이에요. 과거 시점에도 지금 값을 써요`
     - `배당 제외 · 가격 수익률만이에요`
     - 재선정 구간이 12개 미만이면: `구간이 적어서 우연일 수 있어요`
- 결과는 저장하지 않는다(시뮬레이션과 같음). 마지막 요약 숫자만 목록 표시용으로 이 탭 세션에 남긴다.

### 7.5 접근성·일관성

- 기존 토큰과 컴포넌트를 쓴다: `Toggle`, `NumberField`, `Sheet`, `Snackbar`, 차트.
- 등락 표시는 ▲▼와 `trendClass`, 색 관례 설정을 따른다.
- 터치 대상은 44px 이상이다. 진행률은 `role=status`로 알린다. axe 검사를 통과해야 한다.

## 9. 다음 단계 (이번 범위 밖)

조건 표(5장)에 줄을 더하는 구조로 붙인다. 각 단계는 따로 설계한다. 데이터 조사 결과(2026-10-16)는 아래와 같다.

| 단계 | 데이터 | 판단 |
|---|---|---|
| 2 재무·가치 | KIS 재무 TR(재무비율·손익·대차). 결산년월은 있고 **공시일은 없다** | 조건부 가능. 공시 지연 규칙(연간 +90일, 분기 +60일)이 필요하다. PER·PBR은 과거 종가 ÷ 그때 공시된 EPS·BPS로 계산한다. 이력 깊이는 실연결 확인이 필요하다. 정밀하게 하려면 DART(키·`corp_code` 매핑)가 필요하다 |
| 3 투자자 매매동향 | KIS 종목별 투자자 일별(FHPTJ04160001). 날짜를 거슬러 조회하고 수량과 금액을 준다 | 가능. 최대 깊이는 실연결 확인이 필요하다. 반영은 하루 늦춘다 |
| 4 환율·유가 | FRED CSV(DEXKOUS, DCOILWTICO, DCOILBRENTEU). 키가 필요 없고 1980년대부터 있다 | 가능. 수집 스크립트에서 함께 받는다(브라우저 CORS 문제 없음) |
| 4 테마 | KIS `theme_code.mst`(현재 편입만), 사용자 정의 묶음 | 가능. 과거 편입 이력이 없다는 한계를 안내한다 |

- 2·3단계의 수집은 같은 스크립트에서 한다. 앱은 지금처럼 수집 파일만 읽으므로 **프록시 허용 목록을 바꿀 필요가 없다.**

## 11. 테스트

### 11.1 단위 테스트
- **조건 계산:** 각 조건의 손계산 값을 맞춘다. 특히 **재선정일 당일 봉을 쓰지 않는지**를 검사한다(당일 봉만 바꿨을 때 선별이 바뀌지 않아야 한다).
- **대장주 순위:** 업종 레벨 1·2, 동률, 업종 코드 없음.
- **재선정일:** 월·분기·반기 첫 거래일, 휴장일, 기간 시작이 비거래일인 경우.
- **선별:** 정렬 기준별, 동률 시 코드순, 상위 N, 통과 0개.
- **① 보유**
  - 동일 비중 수량(정수 주, `maxShares`)
  - 같은 종목 재선정 시 차이만 거래
  - 수수료와 매도세(결제일 기준), 봉 끊김
  - 손계산 값과 일치
- **② 엔진 확장**
  - `buyWindows`가 없으면 기존 테스트 전부 통과하고 결과가 같다.
  - 있으면 창 밖 매수 신호는 건너뛰고(사유 기록) 매도는 계속한다.
- **시장별 보기:** 범위만 바뀌고 나머지 설정은 같다.
- **기준 저장:** 손상 복구(`repaired`), 내보내기·가져오기 포함, 참조 전략 삭제.
- **가져오기:** 손상 파일, 버전 불일치, 길이 불일치, 저장 공간 부족(가짜 `estimate`).

### 11.2 수집 스크립트
녹화된 응답(fixture)과 가짜 서버로 다음을 검사한다.
- 페이징
- 이어 받기
- 수정주가 변경 감지 후 그 종목만 다시 받기
- 끊김 후 재개
- **키·토큰이 출력·파일·오류에 나오지 않음**
- 저장소 안 출력 경로 거부

### 11.3 e2e (4개 화면 크기)
- 데모용 작은 시장 데이터 파일(종목 30개 × 2년, 테스트 fixture)을 쓴다.
- 흐름: 가져오기 → 기준 만들기 → 미리 보기 → 실행 → 결과(요약·시장별·이력) → 관심 그룹 만들기.
- 탭 키보드 이동과 axe 검사를 포함한다.

## 12. 결정 기록

| # | 결정 | 이유 |
|---|---|---|
| 1 | 추천이 아니라 검증 도구 | 사용자 목적이 "내 기준이 괜찮은가" 확인이다 |
| 2 | 과거 시점 선별, 전날까지의 데이터 | 오늘 데이터로 고른 종목을 과거에 돌리면 결과가 부풀려진다 |
| 3 | ①과 ②를 나란히 | 기준의 효과와 매매 규칙의 효과를 나눠 보기 위해 |
| 4 | 사용자 컴퓨터에서 비주기 수집 | 전 종목이 필요하다. 브라우저 호출로는 느리다. CI에 키를 넣지 않는다 |
| 5 | 수집 파일은 커밋하지 않음 | 시세 재배포 문제와 저장소 크기 때문이다 |
| 6 | 마스터의 재무·시가총액 스냅샷은 받지 않음 | 과거 시점 검증에 미래 정보가 섞인다 |

| 8 | 엔진은 `buyWindows` 선택 필드만 추가 | 기존 시뮬레이션을 깨지 않고 재사용하기 위해 |
| 9 | Web Worker | 전 종목 × 수년 계산이 메인 스레드를 막는다(시뮬레이션과 다른 판단) |
| 10 | 시뮬레이션 화면 안 탭 | 같은 "검증" 성격이다. 내비게이션을 늘리지 않는다 |
| 11 | 관심 그룹에는 상위 8개 | 기존 그룹 최대 종목 수(`MAX_ITEMS = 8`)를 지킨다 |
