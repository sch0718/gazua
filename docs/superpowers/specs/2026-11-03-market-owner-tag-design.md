# 시장 파일 수집 계정 표시 설계 (2026-11-03)

## 1. 목적과 전제

- KIS 약관 제5조 ③ 때문에 시장 파일을 다른 사람에게 주지 않기로 했다(2026-11-03 사용자 결정).
- 곧 초대 가입으로 지인 테스터가 로그인한다. 사용자가 실수로 파일을 건네도 테스터의 앱이 가져오지 않게 한다.
- 우회는 막지 않는다(파일을 고쳐 표시를 지우면 들어간다). 실수 방지가 목적이다. 암호화는 하지 않는다.
- 전제: 사용자 1명(+지인 몇 명), 수집은 사용자 맥에서만, 무료 운영.

이미 있는 것으로 안 되는 이유: 지금 파일에는 누가 수집했는지 알 수 있는 값이 없어, 앱이 남의 파일을 가릴 수 없다.

## 2. 계정 표시(owner)

- 값: `SHA-256("gazua-market-owner/v1\n" + sub)`의 hex 앞 32자(128비트).
  - `sub`는 동기화 계정 식별자다. 서버 `users.firebase_sub`와 앱 `OWNER_KEY` 메타(`ownerId`)가 같은 값이다(Google은 Firebase uid, 카카오·네이버는 `kakao:<id>`·`naver:<id>`).
  - 이메일을 쓰지 않는다. 해시라 파일에서 계정이 드러나지 않는다.
  - 한계: 카카오 회원번호처럼 숫자 ID는 전수 대입으로 되돌릴 수 있다. 파일을 가진 사람은 이미 사용자에게서 파일을 받은 사람이라 영향이 작아 받아들인다.
- 계산 함수 하나(`src/lib/marketData/owner.ts`의 `marketOwnerTag(sub)`)를 앱과 sync-worker가 함께 쓴다(sync-worker는 이미 `src/lib`을 가져다 쓴다). Web Crypto만 쓴다.

## 3. 파일 형식

- 최상위에 선택 필드 `owner?: string`(32자 소문자 hex)을 더한다. v1~v4 모두에 붙을 수 있다. 형식 버전은 올리지 않는다.
  - 옛 앱은 모르는 필드를 무시하고 가져온다. 앱은 자동 업데이트되므로 따로 막지 않는다.
- `validateMarketData`: `owner`가 있는데 모양이 틀리면 `format`.

## 4. 수집 스크립트가 표시를 얻는 방법

새 로그인 흐름은 만들지 않고 기존 CLI 로그인 토큰을 쓴다.

- 서버: CLI 토큰 경로에 `GET /v1/cli/owner`를 더한다. `read`·`market-upload` 두 범위 모두 허용한다. 응답 `{ owner }`(위 2절 값, 서버가 `firebase_sub`로 계산).
- CLI: `gazua owner` 명령. `auth.json`(gazua login)이 있으면 그것을, 없으면 `drive-auth.json`(gazua drive login)을 쓴다. 둘 다 없으면 `not-logged-in`.
  - 옛 Worker는 이 경로를 모르므로 403 `cli-scope`가 온다 → 「서버 업데이트가 필요해요」로 바꿔 알린다.
- 수집 스크립트(`collect-market-data.mjs`): 수집을 시작하기 **전에** `node cli/dist/gazua.mjs owner`를 실행해 값을 받고, 최종 파일의 `owner`에 넣는다.
  - 실패(CLI 빌드 없음, 로그인 안 함, 만료, 서버 옛 버전, 오프라인)하면 수집을 시작하지 않고 이유와 해결 방법을 알린 뒤 끝낸다. 수십 분 수집 뒤에 실패하지 않게 맨 앞에서 본다.
  - `--no-owner`를 주면 표시 없이 수집한다(로그인 없는 개발·시험용). 이 파일은 5절 규칙에 따라 어느 앱이든 가져온다.
  - 근거: 표시 없는 파일을 기본으로 허용하면 이 기능이 의미가 없다. 사용자는 이미 `--drive`를 위해 CLI 로그인을 해 두었으므로 평소 흐름은 Worker 배포 뒤 그대로 돈다.
- `--update`: 이전 파일의 `owner`는 쓰지 않고 이번에 받은 값을 넣는다.

## 5. 앱의 가져오기 규칙

`importFile`이 형식 검사 바로 뒤에 본다. 수동 가져오기(설정 › 데이터)와 Drive 받기가 모두 `importFile`을 거치므로 한 곳에서 처리한다.

| 파일 | 앱 상태 | 결과 |
|---|---|---|
| `owner` 없음(옛 파일, 데모 데이터, `--no-owner`) | 무관 | 가져온다 |
| `owner` 있음 | 로그인, 표시 같음 | 가져온다 |
| `owner` 있음 | 로그인, 표시 다름 | 거절 `owner-mismatch` |
| `owner` 있음 | 로그인 안 함(동기화 설정 없음 포함) | 거절 `owner-signed-out` |

- 옛 파일을 받는 근거: 사용자가 이미 가진 파일과 데모 데이터가 계속 돌아야 한다. 새로 수집하는 파일부터 표시가 붙으므로 시간이 지나면 옛 파일은 사라진다.
- 로그인 안 한 앱을 거절하는 근거: 비교할 계정이 없으면 남의 파일인지 알 수 없다. 테스터가 로그인하지 않고 가져오는 길을 남기면 기능이 의미가 없다. 사용자 본인은 늘 로그인해 쓴다.
- 「로그인」은 동기화 컨트롤러의 `account`가 있는 상태다. `ownerId`는 기기 메타에 남아 있어 오프라인에서도 비교한다(네트워크 호출 없음).
- 이미 가져온 데이터는 다시 검사하지 않는다(로그아웃해도 쓰던 데이터는 그대로).
- 주입: `ImportDeps.owner?: () => Promise<string | null>`. 없으면 로그인 안 함으로 본다. 동기화 컨트롤러에 `marketOwner(): Promise<string | null>`을 더해 화면이 넘긴다. Drive 받기는 클릭 처리기에서 팝업 전에 await하지 않도록 함수 형태로 넘기고 `importFile` 안에서 부른다.

### 안내 문구

- `owner-mismatch`: 「다른 계정에서 수집한 파일이에요. 수집한 계정으로 로그인한 앱에서만 가져올 수 있어요」
- `owner-signed-out`: 「수집한 계정으로 로그인한 뒤 가져와 주세요」
- 수동 가져오기는 스낵바, Drive 받기는 기존 오류 줄에 같은 문구를 쓴다.

## 6. 공유 스냅샷·내보내기 점검

- 내보내기(`exportData`): 프로필 설정·관심종목·전략·기준·바구니·(선택)키만 담는다. 시장 데이터 없음.
- 공유 스냅샷(`share/snapshot.ts`): 6종 모두 허용 필드 검사와 100 KB 상한을 거친다. 시장 파일 본문이나 종목별 일봉 배열은 들어갈 필드가 없다. 시뮬레이션·검증 결과에는 수익률 곡선(%)과 거래 가격이 들어가지만, 이는 기존 공유 확장 설계에서 사용자가 정한 계산 결과다(2026-10-29, 결정 6). 이번 범위에서 바꾸지 않는다.
- 결론: 막을 경로 없음. 코드 변경 없음.

## 7. 바꾸지 않는 것

- Drive 업로드(`gazua drive upload`)는 본인 appDataFolder로만 가므로 표시를 검사하지 않는다.
- 이미 기기에 있는 데이터, 동기화, 데모 데이터 생성 스크립트.
- 파일 암호화·서명.

## 8. 배포 순서

1. sync-worker 배포(새 경로). 2. CLI 다시 빌드(`pnpm -C cli build`). 3. 앱 배포. 순서를 어기면 수집 스크립트가 맨 앞에서 「서버 업데이트가 필요해요」로 멈추고, 그동안은 `--no-owner`로 수집할 수 있다.
